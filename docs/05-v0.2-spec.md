# JudgmentOS — MVP v0.2 Build Spec

Status: Approved for autonomous implementation
Purpose: Close the complete Judgment Loop and add the first AI Advisor capabilities.

---

# 0. Mission

Build a usable JudgmentOS MVP that can take a real-world goal from:

Goal
→ Uncertainty
→ Milestone
→ Evidence
→ Belief Update
→ Decision
→ Action / Experiment
→ Real-world Feedback
→ Learning
→ Updated Reality
→ Dynamic Replanning

The product must help the user reduce uncertainty and make better judgments.

It must NOT become:

- a todo manager
- a generic project manager
- an AI chatbot
- an AI that simply tells the user what to do

Core principle:

> AI proposes, researches, analyzes and challenges.
> The human owns consequential decisions.

# 4. Product Invariants

These rules MUST remain true regardless of implementation.

## 4.1 Milestones reduce uncertainty

A milestone is not merely work to complete.

Every milestone must identify:

- uncertainty being reduced
- purpose
- expected learning
- actual learning when completed

No generic TODO milestones.

---

## 4.2 Human owns decisions

AI may:

- recommend
- challenge
- research
- compare
- explain
- identify risks

AI may NOT silently make consequential decisions for the user.

Human must be able to:

- reject AI recommendation
- select another option
- modify milestones
- delete milestones
- add milestones
- reopen decisions
- change deadlines

---

## 4.3 Expose tradeoffs

Never hide the cost of a recommendation.

When relevant show:

- benefit
- downside
- uncertainty
- cost of waiting
- cost of being wrong
- reversibility

---

## 4.4 Preserve reasoning

Never store only:

decision = X

Preserve:

- alternatives considered
- evidence available at the time
- remaining unknowns
- AI recommendation
- reasoning
- user reasoning when provided
- expected outcome
- timestamp

History must not be overwritten.

---

## 4.5 Evidence is not truth

Separate:

- observation
- source claim
- fact
- assumption
- inference
- opinion

Evidence must also have strength.

Stated intention must not be treated as equivalent to observed behavior.

Example:

"I would pay ¥199"

is weaker evidence than:

"User actually paid ¥199."

---

## 4.6 Reality outranks reasoning

AI reasoning does not validate a decision.

Real-world outcomes do.

Feedback must be able to challenge both:

- the user's belief
- the AI's belief

---

## 4.7 Avoid false precision

Do not invent scientific-looking numerical confidence scores unless a
defined scoring methodology exists.

Prefer qualitative explanations when appropriate.

# 5. Feature 07 — Decision Gate

After evidence / belief updates, evaluate:

> Do we need more information, or is it time to act?

Return:

KEEP_RESEARCHING

MAKE_PROVISIONAL_DECISION

READY_TO_FREEZE

Evaluate:

- decision currently blocked
- evidence supporting alternatives
- missing evidence
- value of additional information
- cost of waiting
- cost of being wrong
- reversibility
- whether additional information is likely to change the next action

Always explain WHY.

Do not require certainty.

---

# 6. Feature 08 — Decision Workspace

When a decision is ready, present a Decision Surface.

Display:

DECISION QUESTION

OPTIONS

For each option:

- supporting evidence
- contradicting evidence
- assumptions
- benefits
- downsides
- important unknowns

Also display:

COST OF WAITING

COST OF BEING WRONG

REVERSIBILITY

AI RECOMMENDATION

AI REASONING

Then:

HUMAN DECISION

Possible statuses:

OPEN
PROVISIONAL
FROZEN
REOPENED

The human can disagree with AI.

Persist disagreement.

Never rewrite history.

---

# 7. Feature 09 — Action / Experiment

A decision should produce a testable interaction with reality whenever possible.

Store:

- action / experiment
- hypothesis
- expected outcome
- evidence expected
- deadline if applicable

Example:

Decision:
Target procrastinating knowledge workers first.

Experiment:
Offer JudgmentOS to 10 potential users for ¥199/year.

Expected outcome:
At least 2 users make a real payment.

The action is not "complete project."

It exists to generate information.

---

# 8. Feature 10 — Feedback Loop

After an experiment, require:

EXPECTED

ACTUAL

DIFFERENCE

LEARNING

Example:

Expected:
2/10 pay ¥199.

Actual:
0/10 paid.
4/10 said they liked it.

Learning:
Stated interest does not currently convert into willingness to pay.

The system should then identify:

- assumptions strengthened
- assumptions weakened
- uncertainties reduced
- new uncertainties introduced

Feedback may:

- support a decision
- weaken a decision
- invalidate a decision
- trigger reopening

Milestone terminal state should represent:

LEARNING_CAPTURED

not generic DONE.

---

# 9. Feature 11 — AI Web Research

The AI may proactively research external information when a milestone
requires external evidence.

Pipeline:

Research Question
→ Search
→ Sources
→ Claims
→ Evidence Classification
→ Evidence Strength
→ Belief Update

Every externally derived claim must preserve its source.

The system must distinguish:

SOURCE SAID X

from:

X IS TRUE

The user must be able to:

- inspect source
- challenge interpretation
- reject evidence
- correct evidence
- add their own evidence

Do not allow web research to become endless research.

Research must serve a specific uncertainty.

---

# 10. Feature 12 — Deadline / Time Engine

Support two timelines simultaneously:

USER DEADLINE

and

SYSTEM RECOMMENDED TIMELINE

The system recommendation must explain why.

If user chooses a shorter deadline, show:

BENEFITS OF COMPRESSION

COSTS

MILESTONES AFFECTED

VALIDATION SACRIFICED

EXPECTED INFORMATION LOSS

DECISION RISK

If the user chooses the recommended timeline, also show its disadvantages.

Never imply:

longer = automatically better.

Time has opportunity cost.

Important concept:

> Cost of waiting must be evaluated alongside cost of uncertainty.

User owns final deadline.

---

# 11. Feature 13 — Dynamic Replanning

Whenever meaningful new evidence, feedback, deadline changes, or decisions occur,
evaluate whether the existing project plan is still valid.

The AI may PROPOSE:

- add milestone
- remove milestone
- modify milestone
- reorder milestone
- reopen decision
- close uncertainty
- introduce new uncertainty

AI must explain:

WHAT CHANGED

WHY THE CURRENT PLAN MAY NO LONGER BE OPTIMAL

PROPOSED CHANGE

EXPECTED BENEFIT

TRADEOFF / RISK

The AI must NOT silently rewrite the plan.

User must approve material changes.

---

# 12. Human Override Protocol

For consequential AI recommendations:

AI proposes:

CHANGE

WHY

BENEFIT

RISK

NEW UNKNOWN INTRODUCED

Then user chooses:

ACCEPT

MODIFY

REJECT

If rejected, preserve the recommendation and rejection in history.

---

# 13. Model Architecture

Do not bind core product behavior directly to a specific model.

Use a provider boundary.

Conceptually:

UI
↓
Application Layer
↓
Decision Engine
↓
Model Provider

Web research should similarly have a replaceable provider boundary.

Do not scatter raw model calls throughout UI components.

Structured outputs should be validated before persistence.

Failures should degrade gracefully.

---

# 14. Judgment Event History

Important state changes should create immutable history events.

Examples:

EVIDENCE_ADDED
BELIEF_UPDATED
DECISION_GATE_CHANGED
DECISION_CREATED
DECISION_FROZEN
DECISION_REOPENED
EXPERIMENT_STARTED
FEEDBACK_CAPTURED
UNCERTAINTY_UPDATED
MILESTONE_ADDED
MILESTONE_REMOVED
PLAN_REVISED
DEADLINE_CHANGED

The current state may change.

History should remain reconstructable.

Goal:

In the future the system should be able to answer:

"What did we believe when we made this decision?"

# 19. End-to-End Acceptance Scenario

Use this as the primary product test.

PROJECT:

JudgmentOS Commercialization

GOAL:

Find a concrete value proposition that real users will pay for.

SUCCESS:

At least 3 external users make or credibly commit to a ≥ ¥199/year purchase.

---

INITIAL UNCERTAINTY:

Who will pay for JudgmentOS and what outcome are they paying for?

---

MILESTONE:

Interview 5–8 potential paying users.

Expected learning:

Identify concrete paying scenarios.

---

EVIDENCE 1:

A student says:

"I procrastinate and I would pay for this."

Expected system behavior:

- recognize positive stated intention
- classify it as relatively weak evidence
- do NOT conclude willingness-to-pay is validated
- update belief
- preserve remaining unknowns
- Decision Gate likely remains KEEP_RESEARCHING

---

EVIDENCE 2:

Another user says:

"I like it, but I would not pay for it."

Expected:

- preserve conflicting evidence
- update belief rather than overwrite previous evidence
- explain what uncertainty remains

---

EVIDENCE 3:

A real user pays ¥199.

Expected:

- recognize behavioral evidence as materially stronger
- update belief
- reevaluate Decision Gate

---

DECISION:

Choose whether to provisionally target this user segment.

Expected:

- alternatives visible
- evidence visible
- tradeoffs visible
- AI recommendation visible
- human makes final decision

---

EXPERIMENT:

Offer the same proposition to 10 similar users.

Expected:

2+ payments.

---

REALITY:

0 pay.
4 say they like the product.

Expected system behavior:

- compare expected vs actual
- capture learning
- weaken relevant assumptions
- reevaluate the decision
- potentially reopen it
- propose project replanning
- require human approval before material plan changes

---

DEADLINE CHANGE:

User changes validation deadline from 14 days to 5 days.

Expected:

- system does not reject change
- identifies compressed validation
- explains information likely sacrificed
- explains benefits of moving faster
- lets user choose

# 20. Acceptance Criteria

MVP v0.2 is NOT complete merely because all screens exist.

It is complete when:

1. The end-to-end scenario above works.

2. State persists across reloads.

3. Historical reasoning is preserved.

4. Conflicting evidence can coexist.

5. Real-world feedback can change beliefs.

6. Feedback can trigger decision reevaluation.

7. AI can recommend plan changes without silently applying them.

8. User can override AI throughout the loop.

9. Web research preserves source provenance.

10. Deadline compression visibly exposes tradeoffs.

11. Model calls are separated from core UI/business logic.

12. Existing working functionality remains functional.

A user can take one consequential real-world goal through:

uncertainty
→ evidence
→ decision
→ action
→ reality
→ learning
→ replanning

without leaving the conceptual JudgmentOS workflow.

The result must preserve enough historical context that the user can later answer:

> What did I decide?
